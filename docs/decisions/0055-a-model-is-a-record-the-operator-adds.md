# 0055 — A model is a record the operator adds, not a protocol frozen in code

Status: accepted 2026-11-20 · decision by the operator

## 1. The question

The worker holds a model's address, model name and key in its configuration, and no code turns them
into a call: `ModelClient` has exactly one implementation, a recorder built for tests. The protocol
appears in no record and no document.

The operator's answer was not a choice between protocols. It was: *it must be customizable at the
end user — several models, several products, addable later, the way the harness application does it.*

## 2. The decision

| What | The rule |
|---|---|
| a model | a **record**, not a compile-time constant: a name, a base address, a protocol, a model id, a sealed key, whether it is enabled, and which one is the default |
| who adds one | an operator with the right permission, on a page, several may exist at once |
| the worker | reads the **effective** record for the job; it can be pointed at a different model without a code change |
| the protocol | an **adapter named by the record**; `openai-chat` is the first, and a second is a new value, not a fork of the pipeline |
| the key | sealed like every secret (`0054`), never read back, never printed |
| traceability | a job records which model record produced it, so a generated task can be traced to the model that wrote it |
| what is not allowed | a hardcoded provider, a key in a committed file, or a pipeline that can call only one shape |

## 3. Why

Models change faster than a pipeline does. Freezing one vendor's request shape into the worker means
every change of model is a code change and a release, and it makes the second model impossible to add
without editing the first one's code path.

A record also buys evidence the project did not have: *this task was generated by that model, at that
version* is a query once the job names it, and it is a guess today.

## 4. Consequences

- A table for model records, a page that adds and edits them, and a sealed key — so `0054`'s sealing
  becomes a prerequisite for the first usable model, not only for the mail password.
- `ModelClient` gains one implementation per adapter, selected by the record; the pipeline does not
  know which one it holds.
- The configuration keys stop being the whole story: they seed the first record, or they name the
  default record's identity, and the worker's configuration surface says which.
- A job row (or its artefact) names the model record it used, so the certificate chain can answer
  "which model produced this".
- Until the table, the page and the adapter exist, the worker passes a client that refuses by name —
  an honest gap, and one that cannot be mistaken for a working model.

## 5. What was rejected

- **One hardcoded OpenAI-compatible client.** It answers "which protocol" and refuses the question
  that was asked: how a second model, or a new shape, is added later without editing code.
- **A vendor SDK per provider.** Each is another dependency with its own key handling, and the choice
  is still frozen at build time.
- **A local server only.** It decides the hardware question by accident.
