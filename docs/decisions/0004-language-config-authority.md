# 0004 — Configuration as data, authority, and the query layer

Status: accepted 2026-10-28 · the language matrix is 0006

## 1. The language matrix is 0006

Which component is written in which language is recorded once, in
[`0006`](0006-language-matrix.md), and this record does not restate it. What follows is the part 0006
does not cover: how the C++ layer reaches the database, and why the browser is not written in C++.

**The browser is HTML.** A browser executes HTML, CSS, JavaScript and WebAssembly, and WebAssembly
"cannot currently directly access the DOM; it can only call JavaScript" (MDN, modified 2026-10-07).
Every C++ frontend is therefore a canvas that re-implements text input, focus and the accessibility
tree, or a server that emits HTML. Qt for WebAssembly, Slint, RmlUi, Wt, Cheerp and Dear ImGui were
each measured against that, and the evidence is in `.agents/memos/2026-10-29-decisions.md`.

**The query layer is sqlpp23 0.70, executed through a Drogon connector.** Two libraries answer
different questions: sqlpp23 checks a statement against the table definitions at compile time — a
renamed column, a missing non-default field, a type mismatch — and Drogon owns the asynchronous
Postgres pool that already belongs to the request's event loop. Neither is a good execution path
alone: sqlpp23's own connector speaks blocking libpq, which is the property that rejected libpqxx
above, and Drogon's query API accepts SQL only as text, which is what sqlpp23 exists to remove.

So the connector is the seam. `core/db/` implements sqlpp23's connection interface, collects bound
parameters in order, executes the serialized `$n` statement through `execSqlCoro`, and decodes rows
back into sqlpp23 result types. Table definitions are generated by `sqlpp23-ddl2cpp` from the plan
pgschema renders, so the schema keeps one source and the C++ header is a derived artifact.

Cost accepted: `core/db/` is a component only this project exercises, against a library at 0.70 with
no 1.0 API promise. It is pinned by tag and covered by round-trip tests that run against the real
PostgreSQL, not a mock.

## 2. Configuration is data

A value lives in Postgres unless it is needed to reach Postgres. Four layers and nothing else:

1. **Host file**, read-only, `0600`: `CMSLEARN_DATABASE_URL`, `CMSLEARN_SEAL_KEY`,
   `CMSLEARN_BOOTSTRAP_ADMIN`, TLS mode. Storing the connection string in the database is circular,
   and the key that unseals secrets must not sit beside the ciphertext.
2. **`settings` rows**: policy, limits, rate limits, routing, image digests, feature flags, sealed
   credentials.
3. **Content tables**: the task bank, seeded idempotently by content hash, then live.
4. **Code**: capability names and each setting's declaration — type, range, default, tier, whether it
   is secret.

**Hot reload.** A row-level trigger on `settings` bumps `settings_meta.version` and calls
`pg_notify` with that number and nothing else. Each process holds
`std::atomic<std::shared_ptr<const SettingsSnapshot>>`, so the hot path is one atomic load. A
notification at or below the current version is ignored, which makes duplicate and reordered
deliveries harmless. Every 30 seconds one `SELECT version FROM settings_meta` runs as a fallback,
because a notification reaches only a connected listener — that fallback is the answer to the failure
mode that makes a naive NOTIFY-only design silently wrong.

**Privileged changes are two-phase**, the same shape as a migration: a plan returns the diff and the
blast radius, an apply takes the plan id.

Where the fact cannot be hot-reloaded it is still admin-editable: routing and rate limits render the
Caddyfile and reach it through `POST /adapt` then `POST /load`; image versions are `release.toml`
digests applied by `compose pull` and `up -d --wait`; schema is `deploy/schema/` through
`pgschema plan` then `apply --plan`. DSN, listen port and seal key are never — changing them is a host
operation by definition.

## 3. Authority: `system:root` is a non-login principal

One full-permission principal that cannot be logged in as, acting through the same core code as every
other actor, with human attribution on every row it writes.

- **Capabilities are an enumerated bitmask.** Names are compile-time constants, the role-to-capability
  mapping is data, and a wildcard is unrepresentable. Editing a row can grant an existing capability
  and can never mint one. The check is one `AND` against the snapshot the request already holds.
- **Root cannot log in, enforced three ways**: system principals carry no password hash, the login
  query filters on `kind = 'user'`, and a composite foreign key plus a `CHECK` makes a session row for
  a system principal unrepresentable. `/admin/*` exists only on `/run/cmslearn/admin.sock` behind
  `SO_PEERCRED`, never on the public listener, and `cmsctl` holds no `DATABASE_URL`.
- **Every audit row records the actor and `invoked_by`** — the host key fingerprint or the elevation
  ticket. The actor is derived from the authenticated principal, never read from a body or header.
- **Elevation is time-boxed to 60 minutes** and irreversible operations require a second approver.
- **Bootstrap is an identity, not a branch**: one transaction inserts a bootstrap principal, creates
  the first human admin and `system:root`, zeroes the bootstrap capabilities, writes the audit row and
  commits. No `if (database_empty)` path survives.
- **`settings_audit` is written by a `SECURITY DEFINER` trigger**, and the application role holds
  `SELECT` only. A forged audit row fails on the grant rather than on a convention, and the trigger
  stores `<redacted>` for a secret.

The invariants the schema enforces are in `docs/schema.md`.

## 4. Schema ownership

`deploy/schema/` is the only DDL, rendered by **pgschema 1.13.4** (Apache-2.0, no login, no paid
tier). `plan` writes the migration to a file before anything runs; `apply --plan` refuses a plan the
database has moved underneath. Online DDL is not opt-in: `CREATE INDEX CONCURRENTLY`, and constraints
as `ADD CONSTRAINT … NOT VALID` then `VALIDATE CONSTRAINT`.

pgschema owns a schema, not a cluster, so `deploy/roles.sql` runs before every apply — an idempotent
creation of `cmslearn_app`, `cmslearn_judge`, `cmslearn_migrate` and `cmslearn_backup`. Extensions are
a bootstrap fact, never a line in a schema file. The plan database is a second database in the same
cluster, named by `--plan-*`, so no embedded Postgres is downloaded at runtime.

Why not Atlas, `pg-schema-diff`, `psqldef`, `migra`, `pgroll`, `pgquarrel` or `@supabase/pg-delta`:
`.agents/memos/2026-10-29-decisions.md`.

## 5. Consequences

- `REGISTRATION_OPEN`, `APPROVAL_REQUIRED`, `ALLOWED_EMAIL_DOMAINS` and `SESSION_TTL_MINUTES` stop
  being environment variables and become settings rows.
- `web/` is a C++ target; `web/tokens.css` and `web/public/fonts/` stay as they are — they are the
  theme, not the framework.
- `content/` becomes the seed rather than the live source, so the content gate runs against the
  database as well as against files.
- Three toolchains are pinned, and two languages appear in the admin path.

## 6. Gates this decision creates

- `check:schema` — `pgschema plan` against a fresh database produces an empty plan.
- `check:stack` — the rendered compose file equals the committed one.
- `check:settings` — every key read by code exists in the settings schema, and every default validates
  against its declaration.
- `check:release` — `release.toml` matches the tag, and every image carries a digest.

Each ships with a falsification case that plants the defect, matching `tools/falsify-*.sh`.
